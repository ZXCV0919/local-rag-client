# 技术取舍（一页）

> 本地知识库桌面端 · 供面试快速对齐边界  
> 更新日期：2026-07-31

---

## 1. 为什么嵌入必须本地？

| 选项 | 结论 |
|------|------|
| 本地 Ollama 嵌入（现状） | **默认**。知识向量不出境，符合「本地知识库」产品名 |
| 云端 Embedding API | 能做，但片段原文会离开本机；且换模型必须**整库重嵌** |

生成可以切 SiliconFlow，是因为「答案怎么写」和「库里有什么」可分离；**检索索引若上云，隐私边界就从『本地库』变成『云 RAG』**，品牌与威胁模型都要重写。故嵌入保持本地。

---

## 2. 为什么不做「全链路可切云」？

全链路 = 云嵌入 + 云向量库 + 云生成。工作量大（重嵌、双栈存储、降级、计费），且会稀释本地卖点。

当前清晰边界：

```
文档 / 分块 / 嵌入 / Chroma+FTS 检索  → 始终本机
对话生成 / 自检 / 可选 LLM 重排       → Ollama 或 SiliconFlow 可切换
```

面试一句话：**本地优先存与检，云端只增强「写答案」的能力。**

---

## 3. API Key 威胁模型

| 层 | 做法 |
|----|------|
| 落盘 | Key 在本机 SQLite（用户机器上的应用数据） |
| 读接口 | `get_setting` / `get_all_settings` 对 Key **只返回掩码** |
| 出站 | SiliconFlow 请求由 **Rust 代理**，前端不再带 `Authorization: Bearer` |

**防的是什么：** WebView/前端脚本、渲染层误把完整 Key 打进日志或网络面板。  
**不防什么：** 本机已获用户权限的进程直接读用户数据目录——桌面应用普遍如此，要 OS 级密钥环可再升级，但不是当前主威胁。

---

## 4. 为什么 PDF 不进解析 Worker？

| 类型 | 策略 |
|------|------|
| md / txt / docx | `parse-chunk` Web Worker，避免大文件卡住 UI |
| PDF | **留在主线程** |

原因：PDF.js 自己已有 Worker；再套一层容易嵌套 Worker / 路径与传输踩坑，收益不稳定。权衡是：**先保证 PDF 正确可用，把最常见的文本类导入移出主线程。**

---

## 5. 重排默认 RRF，而不是默认 LLM？

- **RRF**：稳定、快、可单测、可离线评测回归  
- **LLM listwise**：设置可选；更准潜力，但慢、依赖模型，**fail-open 回退 RRF**

默认选 RRF = 控制延迟与可复现；需要质量时再开第二阶段——这是工程权衡，不是「不会做神经重排」。

---

## 6. 评测怎么讲？

| 命令 | 含义 |
|------|------|
| `npm run eval:retrieval` | mock 向量，CI 可跑，回归融合/门控 |
| `npm run eval:retrieval:live` | **真 Ollama 嵌入** + 同套 golden；可对比 RRF vs LLM 重排 |

live 评测不经 Tauri/Chroma，测的是「嵌入空间 + 融合 + 门控」；应用内 Chroma 路径与之同构，面试时主动说明差异即可。

---

## 一句话收束

本地知识库的核心承诺是**资料与索引在用户机器上**；云端是可选的生成加速器，不是把库搬走。所有取舍都围绕这条承诺展开。
